# КупиДо — описание проекта для дипломной работы

> Документ-справочник с **полной фактической информацией** о веб-платформе «КупиДо».
> Предназначен для использования как контекст при написании выпускной квалификационной
> работы (ВКР / дипломной работы). Содержит только то, что действительно реализовано
> в коде, без вымышленных функций.

---

## 1. Общие сведения

**Название:** КупиДо (КупиДон) — веб-платформа для девелопера / агентства недвижимости.

**Назначение:** онлайн-витрина объектов недвижимости (жилые комплексы и коттеджные
посёлки) с возможностью просмотра, фильтрации, бронирования объектов, подачи заявок
на консультацию, ведения личного кабинета, а также с полноценной административной
панелью для управления контентом и обработки заявок.

**Предметная область:** продажа и аренда первичной недвижимости (новостройки,
загородные дома). Бизнес-роль системы — заменить «звонок менеджеру» онлайн-каталогом
с самостоятельным бронированием и заявками.

**Состав системы (3 приложения):**
1. **Клиентский сайт** (frontend) — публичная витрина + личный кабинет покупателя.
2. **Административная панель** (admin) — управление каталогом, заявками, пользователями.
3. **Backend API** — единое REST-API для обоих фронтендов, бизнес-логика, БД.

**Целевая аудитория:**
- *Гость* — просматривает каталог без регистрации.
- *Зарегистрированный пользователь (покупатель)* — бронирует объекты, оставляет
  заявки и отзывы, ведёт избранное и личный кабинет.
- *Администратор (менеджер девелопера)* — наполняет каталог, обрабатывает брони и
  заявки, модерирует отзывы, управляет пользователями.

## 2. Функциональные возможности (по ролям)

### 2.1. Гость (без авторизации)
- Просмотр каталога проектов с фильтрами (тип, тип сделки, статус, локация, цена).
- Просмотр страницы проекта с фотогалереей и списком объектов.
- Просмотр карточки и страницы отдельного объекта (квартиры/дома).
- Просмотр опубликованных отзывов.
- Ипотечный калькулятор, калькулятор рассрочки, информационные страницы.
- Регистрация и вход.

### 2.2. Зарегистрированный пользователь
- Всё, что доступно гостю, плюс:
- **Бронирование объекта** (с защитой от повторного бронирования того же объекта).
- **Личный кабинет**: профиль (редактирование данных), история бронирований.
- **Избранное** (проекты и объекты, кнопка-«сердечко»).
- **Заявка на консультацию** (доступна только авторизованным — привязывается к клиенту).
- **Отзывы**: оставить отзыв (публикуется после модерации), удалить свой отзыв.

### 2.3. Администратор
- **Дашборд** с агрегированной статистикой и графиками (Recharts).
- **CRUD проектов**: создание/редактирование/удаление, загрузка и сортировка фото
  (drag-and-drop порядок, выбор обложки).
- **CRUD объектов** (квартир/домов) внутри проектов.
- **Управление бронированиями**: смена статуса брони, статуса оплаты и суммы оплаты.
- **Заявки на консультацию**: просмотр, отметка «обработано», запись результата.
- **Модерация отзывов**: публикация/снятие с публикации, удаление.
- **Управление пользователями**: список с поиском, просмотр карточки клиента
  (его брони, заявки, отзывы), редактирование, удаление.

## 3. Архитектура системы

Классическая **трёхзвенная (three-tier) клиент-серверная архитектура**:

```
┌─────────────────────┐     ┌─────────────────────┐
│  Клиентский сайт     │     │  Админ-панель        │
│  React SPA (Nginx)   │     │  React SPA (Nginx)   │
│  порт 80             │     │  порт 8081           │
└──────────┬──────────┘     └──────────┬──────────┘
           │  HTTP/JSON (REST)         │
           │  Authorization: Bearer    │
           └───────────┬───────────────┘
                       ▼
            ┌─────────────────────┐
            │  Backend API         │
            │  FastAPI (Uvicorn)   │
            │  порт 8000           │
            │  • REST /api/v1/*    │
            │  • JWT-авторизация   │
            │  • Раздача /media/*  │
            └──────────┬──────────┘
                       │  async SQL (asyncpg)
                       ▼
            ┌─────────────────────┐
            │  PostgreSQL 16       │
            │  порт 5432           │
            └─────────────────────┘
```

**Ключевые архитектурные решения:**
- **Разделение фронтендов**: публичный сайт и админка — два независимых SPA, чтобы
  изолировать клиентскую и управляющую части (разные сборки, разные контейнеры).
- **Единое API**: оба фронтенда работают через один backend, что исключает дублирование
  бизнес-логики.
- **Stateless-авторизация**: JWT-токены, сервер не хранит сессии.
- **Асинхронность**: весь backend полностью асинхронный (async/await, asyncpg) —
  выдерживает много одновременных соединений при низком потреблении ресурсов.
- **Reverse proxy (Nginx)**: каждый фронтенд раздаётся через Nginx, который также
  проксирует запросы `/api/` и `/media/` на backend (избегаются проблемы CORS и
  смешанного контента в продакшене).
- **Контейнеризация**: вся система разворачивается одной командой через Docker Compose.

- `users` 1 — ∞ `reviews`, `favorites`, `consultation_requests`.
- `building_projects` 1 — ∞ `reviews`, `consultation_requests` (через nullable FK).

## 6. Миграции базы данных (Alembic)

Схема и начальные данные версионируются миграциями. На старте контейнера выполняется
`alembic upgrade head` — поэтому БД разворачивается «из коробки».

| Ревизия | Содержание |
|---|---|
| 001 | Начальная схема (все таблицы), seed-данные (служебные пользователи) |
| 002 | Добавление статуса оплаты в брони (`payment_status`) |
| 003 | Поле `deal_type` у проектов; таблицы `reviews` и `favorites`; поля `result`/`user_id` в заявках; очистка демо-броней |
| 004 | Замена служебных email (`@localhost` → `@kupido.ru`) |
| 005 | Замена демо-каталога на расширенный (5 проектов / 16 объектов всех категорий) |

## 8. Авторизация и безопасность

- **Аутентификация — JWT** (JSON Web Token), алгоритм **HS256**. При входе сервер
  выдаёт `access_token`; клиент хранит его и передаёт в заголовке
  `Authorization: Bearer <token>`. Срок жизни — 1440 минут (24 ч) по умолчанию.
- **Пароли** хранятся как хеши **bcrypt** (12 раундов), исходные пароли не сохраняются.
- **Ролевая модель**: две роли — `user` и `admin`. Доступ к управляющим эндпоинтам
  ограничен зависимостью `get_current_admin` (HTTP 403 при недостатке прав).
- **Stateless**: сервер не хранит сессии, что упрощает горизонтальное масштабирование.
- **CORS**: разрешённые источники настраиваются через `CORS_ORIGINS`.
- **Валидация ввода**: Pydantic-схемы; телефон проверяется регулярным выражением
  под формат РФ (`+7`/`8`), email — `email-validator`.
- **Загрузка файлов**: ограничение по расширению (jpg/jpeg/png/webp) и размеру (10 МБ).
- **Контроль владельца**: пользователь видит/удаляет только свои брони/отзывы;
  изменение статусов броней и модерация — только админ.

## 9. Ключевые бизнес-сценарии

### 9.1. Бронирование объекта
1. Авторизованный пользователь на странице объекта со статусом `available` нажимает
   «Забронировать», заполняет комментарий.
2. Backend проверяет, нет ли у пользователя уже активной брони на этот объект; при
   наличии — HTTP 409 «Вы уже забронировали этот объект» (защита от дублей).
3. Создаётся бронь со статусом `pending` и `payment_status = not_paid`.
4. Администратор в панели меняет статус брони (подтверждение/отмена), фиксирует
   статус и сумму оплаты.

### 9.2. Модерация отзывов
1. Пользователь оставляет отзыв → создаётся с `is_published = false`.
2. На публичном сайте видны только опубликованные отзывы.
3. Администратор видит все отзывы (`all=true`) и публикует/снимает их.

### 9.3. Заявка на консультацию
- Оставлять заявки могут только авторизованные пользователи (заявка привязывается к
  клиенту через `user_id`). Администратор обрабатывает заявку и записывает результат.

### 9.4. Избранное
- Кнопка-«сердечко» на карточках проектов и объектов. Уникальные ограничения в БД не
  позволяют добавить дубликат. Удаление возможно по id записи или по объекту.

### 9.5. Личный кабинет
- Просмотр и редактирование профиля, история бронирований, избранное, свои отзывы.

## 12. Хранение медиафайлов (особенность реализации)

Фотографии каталога хранятся **в репозитории** вместе с кодом (вариант «фото в git»):
файлы лежат в `backend/media/`, а их метаданные дублируются в `manifest.json`.

Механизм синхронизации (выполняется при старте backend, в lifespan-хуке FastAPI):
1. **Восстановление из манифеста** — после `docker compose down -v` (когда БД пустая,
   а файлы пришли с репозиторием) записи таблицы `photos` восстанавливаются из
   `manifest.json`. Это обеспечивает наличие фото «из коробки».
2. **Уборка осиротевших файлов** — удаляются изображения, на которые нет ссылок ни в
   БД, ни в манифесте.

Раздача файлов: backend монтирует каталог `media` как статику по пути `/media`;
Nginx во фронтендах проксирует `/media/` на backend.

## 13. Развёртывание (Docker)

Запуск всей системы одной командой:
```bash
docker compose up --build -d
```

**Сервисы `docker-compose.yml`:**
| Сервис | Образ/сборка | Порт | Назначение |
|---|---|---|---|
| db | postgres:16-alpine | 5432 (внутр.) | База данных, том `pgdata` |
| backend | ./backend (Python 3.12) | 8000 | API, том `media` |
| frontend | ./frontend (Nginx) | 80 | Клиентский сайт |
| admin | ./admin (Nginx) | 8081 | Админ-панель |

**Точки доступа:**
- Сайт — http://localhost
- Админ-панель — http://localhost:8081
- API (Swagger) — http://localhost:8000/api/docs

**Процесс старта backend (`start.sh`):** применение миграций (`alembic upgrade head`)
→ запуск Uvicorn. На старте также синхронизируются медиа (см. §12).

**Особенность кроссплатформенности:** в репозитории есть `.gitattributes`,
фиксирующий LF-переносы строк для shell-скриптов, и защита в `Dockerfile`
(`sed`-нормализация `start.sh`) — чтобы сборка работала и при клоне на Windows
(где иначе CRLF ломает shebang).

## 16. Возможные направления развития (для раздела «перспективы»)

Эти возможности **не реализованы**, но логично вытекают из архитектуры и подойдут для
раздела о перспективах развития:
- Онлайн-оплата брони (эквайринг) вместо ручной фиксации оплаты.

- Email/SMS-уведомления о статусе брони и заявки.
- Полнотекстовый поиск и расширенные фильтры каталога.
- Корректное отображение цен аренды (сейчас вёрстка ориентирована на цены продажи).
- Автотесты (unit/integration), CI/CD-пайплайн.
- Вынос медиа в объектное хранилище (S3) вместо хранения в репозитории.
